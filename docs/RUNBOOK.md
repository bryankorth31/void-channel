# Runbook: keeping VOIDtv healthy without help

The system is built to run itself: the builder hunts and matches on this PC, the two-hour publish and
the 3:30 nightly push the catalog, Cloudflare rebuilds the site. The **doctor** (`node scripts/doctor.js`,
run nightly and from HQ > Overview) turns the moving parts into lights. This page says what each light
means and what to do. Everything here is clickable in HQ or a one-line command.

## The lights

| Light | Green | Yellow | Red and what to do |
|---|---|---|---|
| publish | the last run pushed, or found nothing new, within 6 h | **held**: the catalog is committed but not pushed because commits from other chats are waiting (see unpushed); or no publish run for 6 h+ | **FAILED** or **refused**: open HQ > Jobs > publish.log, the last dated line says why. FAILED: a file git cannot add (odd name, locked by a job), a push that did not go through after three retries, or a push origin rejected because it has newer commits (pull or rebase by hand). refused: nothing was committed or pushed; the catalog shrank by more than 10% (find out what emptied it; if it is meant, `node scripts/publish.js --allow-shrink`), a catalog file is not valid JSON, or what was about to go out holds an address or a token (the line names the file). Fix the cause and press Publish now. |
| unpushed | nothing waiting on this PC, or a Catalog commit made under 30 min ago | commits from other chats are waiting for your push; the scheduled publish never sends them (it logs held) | a Catalog commit has waited over 30 min: the push failed or is held. Read publish.log, then run `node scripts/publish.js`, which pushes waiting Catalog commits first. To send the other commits together with the catalog, `node scripts/publish.js --allow-other-commits`. |
| addresses | no address-shaped text in the tracked catalog files | | an address-shaped string in a tracked catalog file; the light names the first files. Uploader addresses are other people's data and must not be published: remove the uploader field, or replace the text with [email], in the named file. (Archive file names that only look like an address, such as ones ending .mp4, are not counted. publish.js also refuses to add one.) |
| nightly | finished in the last 30 h, all steps ok | a step failed (hunt, art, people, db...) | no pass in 30 h: the task is missing or the PC was off. HQ > Overview > Re-create scheduled tasks. |
| task: VoidTV Publish / Nightly | scheduled | last result not 0 | missing or disabled: Re-create scheduled tasks (HQ > Overview). |
| jobs | 0 to 2 Archive jobs | | 3+ Archive-facing jobs: stop one in HQ > Jobs; the Archive throttles this address when it is hammered, and that hurts the viewer too. |
| catalog | every grid parses | | unreadable grids or a reserved-name file (con, prn, aux, nul, com1-9, lpt1-9). Re-match the show from HQ; a reserved-name file is deleted with the long path: `node -e "require('fs').unlinkSync('\\\\?\\C:\\path\\con.json')"`. |
| matcher | the self-tests pass; under 5% of the picks whose number and title both fit sit below LIVE; no day of the last 3 holds over 20% of the grids' matchedAt | self-listed grids over a TVmaze list still hold picks from uploads whose title does not name the show: Re-match the listed shows (HQ > Shows > Re-match now). Or 5% or more of the picks whose number and title fit sit below LIVE: the scoring may have slipped, run `node --test tests/match.test.js`, then `node tests/match-dryrun.js` (see the usage line at its top). Or over 20% of the grids carry one matchedAt day from the last 3 days: a run restamped them, and a grid should change only when its content does (a grid still on the day its file was made, such as a new show from a big hunt, is not counted); check that scripts/match.js writes through writeIfChanged. (Right after the first run with the content-only writer one old day can hold most grids; that stops counting once the day is 3 days old.) | a self-test fails: the matcher itself is broken. Run `node --test tests/match.test.js` and do not run a bulk match (HQ > Shows > Re-match all, or `node scripts/match.js`) until it passes. |
| movies:phrase | every LIVE TV movie carries its title as a phrase in the file name or the upload title ("Open Marriage" in "Open Marriage (1985)", not in "Wide Open Marriage") | some LIVE movies do not: the title is only scattered through the name or runs on into a longer title, so another work plays under the film's title (audit CP-022). The light names the first three | n/a. By hand, no AI: `node scripts/hunt-movies.js --rescore` judges every stored pick again with today's rules, needs no network, writes nothing, and prints each LIVE to REVIEW or MISSING change with its reason, then the counts. `node scripts/hunt-movies.js --rescore --write` writes the records that changed (the film keeps its place on the list, as REVIEW, or as MISSING with no file) and docs/MOVIES.md. The rule is in scripts/lib/moviejudge.js; `node --test tests/hunt-movies.test.js` proves it, and `node tests/movies-dryrun.js` (usage line at its top) shows the effect on the real catalog without writing anything. |
| movies:hard-exclude | none of the movie picks the site would ship is C-SPAN, hearing, council, school board, work session, press conference, election or news material | n/a | red: a shipped pick breaks the standing rule that politics, government and news are out (R-005). The light names the first three and says how many are LIVE and how many REVIEW. By hand: the same two `--rescore` commands as movies:phrase drop every such pick and name each one in the log; the film keeps its place on the list. A film whose own title holds one of the words (Election, The Committee) is not punished for its own title. To test one name: `node -e "console.log(require('./scripts/lib/hardexclude').hardExclude({ stem: 'CSPAN2_20201204_Senate_Hearing' }, 'Crossfire'))"` prints what matched, or null for a clean name. The word list is in scripts/lib/hardexclude.js. |
| movies:review-hidden | always green, with the numbers: how many LIVE TV movies the site shows, how many REVIEW movies it keeps hidden, how many approved REVIEW movies it shows, and how many picks the hard-exclude gate skips (0 once the rescore is written). A large hidden number is normal. The site shows a TV movie only when it is LIVE or you approved it; REVIEW means the matcher is not sure the file is the film. TV show episodes are not affected: their REVIEW episodes still show | `catalog/overrides.json` does not parse as JSON (usually a missing comma or quote after a hand edit), so the build ignores every movie approval. Also: some approvals show nothing (the movie has no playable file, or it is C-SPAN, hearing, council or news material: the hard excludes beat an approval) | n/a. By hand, no AI. To see the hidden ones with their ids and addresses: `node -e "const fs=require('fs');for(const f of fs.readdirSync('catalog/movies')){const r=JSON.parse(fs.readFileSync('catalog/movies/'+f,'utf8'));if(r.state==='REVIEW'&&r.file&&r.file.playable)console.log(r.tmdbId,r.title,r.year,'<=',r.file.url)}"`. To watch a file before you decide, open the address that line ends with in a browser. **Approve one movie:** open `catalog/overrides.json` in a text editor and add one entry inside the outer braces, with a comma after it unless it is the last: `"movie-<id>": { "approved": true }` (the id is the first number on that movie's line above, the movie's `tmdbId`; it is also the end of the movie's web address, voidtv.net/show/movie-<id>; the file names in `catalog/movies` are the title and year, not the id; keep catalog/overrides.json valid JSON). The next site build (`node scripts/site.js`, or the publish) puts the movie on the site, and this light's approved count goes up by one. **Un-approve:** delete that entry (or set `"approved": false`) and build again; the movie goes back off the site. A LIVE movie needs no approval. A MISSING movie never ships. HQ has no screen for this yet: its server accepts the key (`POST /api/override/movie-<id>` with `{"set":{"approved":true},"rematch":false}`), but no HQ page sends it for movies, so the file edit is the way today. If the JSON breaks, this light turns yellow; `git diff catalog/overrides.json` shows what changed since the last commit, so the broken spot is easy to find (do not run `git checkout` on that file: it also throws away your other HQ decisions since the last publish). The gate is `movieShips` in `scripts/lib/app.js`; `node --test tests/movies-gate.test.js` proves it. **The first publish after this gate arrives is refused as a shrink** (the show count drops by about a quarter before the rescore, by about 44% after it, because the hidden movies were counted as shows): that is expected, so run `node scripts/publish.js --allow-shrink` once, and for the Cloudflare build set the plain variable `SITE_ALLOW_SHRINK` = `1` for that one deploy and delete it afterwards (see the shrink light). |
| episodes:guess-hidden | always green, with the numbers: how many guessed episodes the site keeps off, in how many shows; how many play a title or number match instead; how many shows that leaves with no episode (they drop off the site); how many guesses you accepted in HQ (those ship). A guessed episode is one scripts/match.js placed by position: the Nth unnamed file of a disc rip taken as episode N (its reason starts with "sequence guess"). Most of the ones that can be checked are wrong (25 Oct 2026: 400 of the 509 whose file name carries its own number disagree), so they ship nowhere, not on show pages, not on Live TV (B, 25 Oct: a wrong episode is worse than a missing one) | the count could not run (the message names the error; usually a show grid that does not parse) | n/a. By hand, no AI. **Confirm one guess:** HQ > Shows > the show > the episode, press the file to preview it; if it really is that episode, press Accept. HQ re-matches the show, the episode turns LIVE and the next publish puts it on the site (this light's accepted count goes up). Reject sends the file away for good. **List the guesses of one show:** `node -e "const g=require('./catalog/shows/<slug>.json');for(const se of g.seasons)for(const e of se.episodes)if(e.file&&/^sequence guess/.test(e.file.why))console.log(se.season+'x'+e.number,e.name,'<=',e.file.name)"` (the slug is the end of the show's web address). The gate is `epNoGuess` in `scripts/lib/app.js`; `node --test tests/episode-guess.test.js` proves it. To stop the matcher guessing for one show at all, set `"noGuess": true` on its entry in `catalog/overrides.json` (SpongeBob has it). |
| build | the page assembles, channels resolve | | assemble() throws or ships under 300 titles: the message names the file. Usually the catalog folder was emptied by a bad command; `git checkout -- catalog` restores it. |
| tv:schedule | every Live TV channel fills today on the 30-minute grid (each show starts on the hour or the half hour, no episode runs past its time, nothing overlaps) and every show the plan names is in the build; the message gives the holding-card minutes an hour | a channel shows more than 20 minutes of holding cards an hour: add your originals in HQ (catalog/fillers.json) or short episodes to that channel, and its breaks fill | shows the plan names are missing, a channel would be left empty, or airings run off the grid: run `node scripts/site.js` again; if it stays red, `node --test tests/tvgrid.test.js` names the broken rule. The live site keeps playing meanwhile: the page drops what it cannot find and holds with the cards. |
| tvmaze / archive / tmdb | reachable | down or token rejected | Nothing to fix on our side; hunts and art pause themselves. A rejected TMDB token: get a new read token, put it in backend/.env. |
| live | voidtv.net serves the commit origin/master points to (as this PC last saw it; the doctor does not fetch), a newer one, or the push is under 10 minutes old and Cloudflare is still building | origin/master is over 10 minutes old and the live site still serves an older commit | Cloudflare did not build the latest push, or the build failed: dash.cloudflare.com > Workers & Pages > voidtvsite > Deployments, open the failed one, the log names the error: a script that does not parse, or one of the build's own refusals (`CATALOG SHRANK`, `SITE TOO BIG FOR PAGES`, `SITE WOULD SHIP WITH n SHOWS`). `node scripts/site.js` here prints the same. A push made from another PC shows up here after you `git pull`. |
| gate | `version.txt` says `gate=on` and the front page answers 401 (the password page), or it says `gate=off`, the front page answers 200 and the analytics intake (`/api/e`) answers 200. With gate=off the message says OPEN: the site is public | `version.txt` has no `gate=` word yet (the live build is older than the one-switch change), or the site did not answer | the build and the running site disagree. gate=on but the front page answers 200: the password is not set where the running site can see it. gate=off but the front page answers 401, or `/api/e` answers 401: SITE_PASSWORD is still set at runtime (usually a Secret the build cannot read) while `GATE` = `off` told the build to open the site. Fix in Workers & Pages > voidtvsite > Settings > Variables and Secrets, Production list: to open the site, delete SITE_PASSWORD; to keep it private, set the Text variable `GATE` to `on`. Then Deployments > latest > Retry deployment. The switch has two plain-text halves: the password closes the site (type Text, or a Text `GATE` = `on` beside a Secret) and only a Text `GATE` = `off` with no password opens it. A Cloudflare build that sees neither stops with `GATE UNKNOWN` and the old site stays up, which is safe: add the variable the log names. docs/DEPLOY.md has the whole switch. |
| files | `version.txt` counts under 18,000 files and no file over 24 MiB (Pages allows 20,000 files and 25 MiB each) | 18,000 to 19,499 files | 19,500 files or more, or a file over 24 MiB. The build refuses to ship at that size and the old site stays up. Fewer per-show pages or a data split is needed (audit F-005): tell the Voidtv chat. The figure grew about 350 files a day in October 2026 while hunts added shows. |
| www | `https://www.voidtv.net/` answers 301 to `https://voidtv.net/` | any other answer | While the password is on, the gate's middleware does the redirect. Once the site is open only a Cloudflare rule can: dash.cloudflare.com > voidtv.net > Rules > Redirect Rules > Create rule, host equals `www.voidtv.net`, dynamic target `concat("https://voidtv.net", http.request.uri.path)`, status 301, keep the query string (docs/DEPLOY.md, opening day). |
| headers | `/` and `/version.txt` both carry Strict-Transport-Security, X-Frame-Options and X-Content-Type-Options | only HSTS is missing | X-Frame-Options or nosniff is missing: the latest deploy did not carry `_headers` and the middleware, check Deployments. HSTS alone is the Cloudflare click: dash.cloudflare.com > voidtv.net > SSL/TLS > Edge Certificates > HTTP Strict Transport Security (HSTS) > Enable HSTS, max age 12 months, leave the subdomain and preload boxes off. |
| shrink | the show count is not down more than 10% against the last publish (`catalog/cache/publish-state.json`) | no publish has run on this PC yet | down more than 10%: something emptied the catalog (a bad match, a cleaned cache folder). Do not publish. Check `git status` in `catalog/` and HQ > Jobs, restore with `git checkout -- catalog`. If the drop is meant, it needs **two overrides**, because the publish and the Cloudflare build each refuse it: `node scripts/publish.js --allow-shrink` lets the push go out, and then on Cloudflare (Workers & Pages > voidtvsite > Settings > Variables and Secrets, Production list) a plain Text variable `SITE_ALLOW_SHRINK` = `1` must be set for that one deploy, followed by Deployments > latest > Retry deployment, and deleted again afterwards. With only the first, the push succeeds, the build is refused and the live site stays on the old commit (the `live` light turns yellow after 10 minutes). |
| backup | `catalog/cache/backup-stamp.json` is under 7 days old and every file was copied | older than 7 days, or the last run could not copy some files | never run. `catalog/cache` is not in git and holds the only copy of every TVmaze episode list. Run `node scripts/backup-cache.js --to D:\void-cache-backup` (any folder outside the repo, ideally another drive). To make a folder the default, put `VOID_BACKUP_DIR=<folder>` in `backend/.env`; the script reads only that key. It copies `tvmaze-*`, `tmdb-*` and `meta-*` files (about 2.4 GB the first time, seconds after that, nothing is ever deleted at the destination) and leaves the `scrape-*` and `mscrape-*` pages (20 GB) out. `node scripts/backup-cache.js --dry` counts without copying; `--only tvmaze` copies just the 32 MB of episode lists. |
| page-guards | the page the build would ship carries the guards: the show-load cards, the kept player across episodes, the leave-during-lookup guard and the safe save of Mine | n/a | red: someone edited `scripts/lib/app.js` and dropped a guard (the message names which text is missing). By hand: open a show that does not exist (`/show/not-a-show`) and expect the home page with one line, not a blank page; open a show, press F, then N, and expect to stay in fullscreen; like a show in one tab, play in another for 10 seconds, reload, and expect the like to survive. Restore the guard from git: `git checkout -- scripts/lib/app.js` |
| live:missing-files | a file that cannot exist (`/assets/zz-check.png`, `/data/shows/zz-check.json`) is answered with the home page (the host's normal fallback, which the page copes with) or 401 behind the password | the host cannot be reached | red: a file that cannot exist came back as JSON, so the host is serving something it should not. Open the Cloudflare dashboard > Workers & Pages > voidtvsite > Deployments and check the latest deploy. Runs only in the full doctor, not `--quick` |
| analytics | token present | not connected | HQ > Reports lists the two one-time Cloudflare steps. |
| links | under 3% of sampled files dead | 3 to 8% | over 8%: the Archive took down a batch. Dead files are retired automatically and alternates picked at the next match; re-hunt the worst shows from HQ (Shows > the show > Re-hunt now) to find new copies. |
| cache | 50 GB or more free on the disk (the cache size is shown, not judged: it grows with the catalog) | | the disk is under 50 GB free. First pack the search pages if a plain one is left: `node scripts/pack-cache.js` (gzip, lossless, about 30% of the size; it refuses while a hunt or the scout runs). Then delete the oldest `catalog/cache/scrape-*`, `mscrape-*` and `scout-*` pages, never while a hunt runs: a hunt fetches them again when it needs them. The doctor already prunes old metadata files. Never delete `tvmaze-*` files: they are the only copy of every episode list (see the backup light). |
| repo | .git under 4 GB | | run `git gc`; when that no longer helps, start a fresh catalog repo (copy `catalog/`, `docs/`, `scripts/show-list.json` into a new repo, point Cloudflare at it). |

## Daily, in HQ (five minutes)

1. Overview: all lights green? If not, the table above.
2. Reports: any Wrong file? reports or playback errors from viewers. Open the show, preview, Reject or Accept. The same page lists Wrong film reports (viewers who ticked "Not the right film" on a TV movie marked "Unconfirmed match"): open the film on voidtv.net and its Archive item side by side. That list is read only and hides nothing.
3. Shows > "review only": watch a minute of a file the judges were unsure about, Accept.
4. Analytics > Searches: zero-result searches are things people want; Add shows.

## Weekly

- Publish now after a session of decisions, so the site catches up without waiting for the schedule.
- Jobs: is the balanced hunt still running? Start it again if the list has unhunted shows (Overview shows hunted of listed).
- Glance at `docs/SELF_LISTED.md` and the shows flagged `tvmazeWeak` in HQ: those are listed from their own files because TVmaze could not place them; a wrong TVmaze id (set it on the show page) often fixes one.

## When Windows changes under us

- Tasks gone after an update or a new user profile: HQ > Overview > Re-create scheduled tasks.
- Node updated: run `node --check scripts/*.js`; nothing else depends on the version.
- New PC: clone the repo, `npm install` is only needed in `hq-app/` to rebuild the desktop app; HQ itself has no dependencies. Put `backend/.env` back (TMDB and analytics tokens). Re-create the tasks.

## What the system protects itself against already

- The site build refuses to ship a page whose script does not parse, has a trailing `//` comment, or carries under 100 titles.
- The matcher survives a corrupt file, re-reads your HQ decisions mid-run, keeps accepted files whatever the judges say, and treats dead files as rejected.
- HQ answers only this PC, validates every slug and argument, and keeps its job list across restarts.
- Every decision you make lives in `catalog/overrides.json` and is committed with the catalog; the builder never overwrites it.
